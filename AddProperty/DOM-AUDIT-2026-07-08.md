## Systemic Issues

### 🔴 CRITICAL: Energy Certificate Extraction is Broken

**Every listing affected.** The icon class name format has changed from `icon-energy-X` (where X was the grade letter) to `icon-energy-c-N` (where `c` is a constant prefix and `N` is a numeric style variant). The actual grade is now in the `title` attribute of the `<span>`.

Evidence across all 9 listings:

| Listing | CSS class | `title` attr (real grade) | Our extraction |
|---------|-----------|---------------------------|----------------|
| 32873256 | `icon-energy-c-11` | `a+` | C |
| 32965889 | `icon-energy-c-11` | `a+` | C |
| 32873242 | `icon-energy-c-11` | `a+` | C |
| 32873209 | `icon-energy-c-11` | `a+` | C |
| 32882817 | `icon-energy-c-4` | `c` | C (coincidence) |
| 32889935 | `icon-energy-c-5` | `d` | C |
| 32917800 | `icon-energy-c-4` | `c` | C (coincidence) |
| 32944777 | `icon-energy-c-4` | `c` | C (coincidence) |
| 32960032 | `icon-energy-c-4` | `c` | C (coincidence) |

**Fix:** content-ad.js should send `energyEl.getAttribute('title')` instead of (or in addition to) `energyEl.className`. IdealistaLocators.cs can then use the title directly instead of regex-parsing the class name.

---

### 🔴 CRITICAL: Location Parsing Fails on Multi-Part Strings

The "known gap" assumption that `.main-info__title-minor` returns only a single value is **wrong**. Observed patterns across 9 listings:

| Parts | Format | Example | Count |
|-------|--------|---------|-------|
| 1 | `Municipality` | `Portimão` | 1/9 |
| 2 | `Zone, Town` | `Vilamoura, Quarteira` / `Portimão Cidade, Portimão` | 4/9 |
| 3 | `SubZone, Zone, Town` or `Zone, Town, Parish` | `Centro da Cidade, Albufeira, Albufeira e Olhos de Água` | 4/9 |

The structure is **most-specific → least-specific** (left to right). The last part is always the Parish/Town name; the first part is the finest-grained zone.

`MarketAreaLookup.Resolve()` treats the full comma-separated string as a single term → always fails for multi-part strings → fallback comma-split has wrong assumptions about which part is which:

| Location text | Fallback result | Correct result |
|--------------|-----------------|----------------|
| `Portimão Cidade, Portimão` | Muni=Portimão, Town=**Portimão Cidade** | Muni=Portimão, Town=Portimão, Zone=Portimão Cidade |
| `Vilamoura, Quarteira` | Muni=**Quarteira**, Town=**Vilamoura** | Muni=Loulé, Town=Quarteira, Zone=Vilamoura |
| `Centro da Cidade, Albufeira, Albufeira e Olhos de Água` | Muni=**Albufeira e Olhos de Água**, Town=**Albufeira** | Muni=Albufeira, Town=Albufeira e Olhos de Água, Zone=Centro da Cidade |
| `Zona Nascente, Quarteira, Quarteira` | Muni=**Quarteira**, Town=Quarteira | Muni=Loulé, Town=Quarteira, Zone=Zona Nascente |

**Fix:** `Resolve()` should split by comma first and try resolving each part, working right-to-left (least specific first). The rightmost part that matches a Town gives the Town+Municipality; the leftmost part is the Zone candidate.

No JSON-LD, no breadcrumb nav, no `og:` geo tags, and no data attributes with finer location info exist anywhere else on the page. The subtitle is the only source.

### 🟡 MODERATE: Condition Parsing Priority with Compound Strings

Idealista uses compound condition strings like `Segunda mão/bom estado` and `Segunda mão/para recuperar`. Our ParseCondition checks in fixed priority order (NewBuild → Renovated → Good → Used → NeedsRenovation), which means `segunda mão` (matching Used) wins over `para recuperar` (matching NeedsRenovation) even though the listing explicitly says it needs renovation.

Suggestion: when the feature text contains `/`, split and take the MORE SPECIFIC qualifier (the one that is a subset of Used → the right side). Or just check NeedsRenovation before Used.

---

### 🟡 MODERATE: Tenanted Exclusion Regex — Feminine Form Gap

`ExclusionPatterns.Tenanted` uses `\barrendado\b` (masculine only). Idealista's feature bullet says `Arrendada` (feminine, agreeing with "propriedade" or the implicit feminine noun). The exclusion still fires via the second alternative `com inquilino` (which is a substring of `com inquilinos`), but if a listing said just "Arrendada" without "com inquilinos", it would slip through.

**Fix:** Change `\barrendado\b` to `\barrendad[oa]\b`.

- **Title (h1):** Clean across all 9 listings. The inner `<span class="main-info__title-main">` is correctly stripped by `innerText`. No hidden spans or whitespace pollution.
- **Price format:** Consistent `NNN.NNN €` format. No "Preço sob consulta" in this sample (none were price-on-request). Price regex works correctly.

- **Description fallback:** `.comment` was present on all 9 listings; `.adCommentsLanguage` was absent on all. No translation notices in this sample. Cannot verify the fallback behavior without a translated listing.
- **Phone/email stripping:** No phone numbers or emails found in any description across all 9 listings. Cannot verify stripping regex accuracy without a description that contains contact info.
- **Coordinates (/mapa page):** Not inspected — would require navigating to /mapa sub-pages, which the audit scope excluded.
